# 예금자보호 법령 RAG 챗봇

예금자보호법과 시행령만 보고 예금자보호 질문에 답하는 챗봇이다. "한 은행에 정기예금 8천만 원, 적금 4천만 원이 있으면 얼마까지 돌려받나요?" 같은 질문에 근거 조문을 붙여 답하고, 법령에서 근거를 찾지 못하면 지어내지 않고 모른다고 한다.

LangGraph, pgvector, OpenAI API(gpt-5.4-mini, text-embedding-3-large)를 쓴다.

## 왜 법령만 쓰나

예금보험공사 안내 페이지가 더 친절하지만 무단 복제와 배포를 금지한다. 법령은 저작권 보호 대상이 아니라서(저작권법 제7조) 원문을 저장소에 함께 둘 수 있다. 조·항·호로 나뉘어 있어 정답 근거를 조항 단위로 붙이기도 좋다.

대신 질문과 법령의 말이 많이 다르다. 사람은 "은행이 망하면", "대출이 있으면"이라고 묻지만 조문은 "보험사고", "예금자등이 해당 부보금융회사에 대하여 지고 있는 채무"라고 쓴다. 이 차이가 검색을 어렵게 만든다.

쓰는 문서는 예금자보호법(2026. 1. 2. 시행, 법률 제21065호)과 시행령(2025. 9. 1. 시행, 대통령령 제35687호)의 본칙이다. 기준일은 2026-10-19이고, 원문은 [국가법령정보센터](https://www.law.go.kr/법령/예금자보호법)에서 받는다. 새마을금고나 우체국 예금은 다른 법률이 다루기 때문에, 물어보면 이 법령으로는 알 수 없다고 답한다.

## 동작

```
질문 → 임베딩 → 검색(벡터 + BM25, 상위 5개 조문) → 생성(답, 인용, 보류 여부) → 인용 검사 → 답 또는 보류
```

법령은 조문 하나를 조각 하나로 색인한다(132개). 검색은 pgvector 코사인 거리로 전부 비교한 상위 20개와 BM25 상위 20개를 RRF로 합쳐 5개를 고른다. 한국어는 조사가 붙어 띄어쓰기 단위로는 "지급한도는"과 "지급한도"가 다른 말이 되므로, BM25는 두 글자씩 잘라 쓴다. 생성 모델은 조각 5개에 C1부터 C5까지 번호를 붙여 받고, 정해진 형식으로 답과 인용 번호, 보류 여부를 돌려준다. 마지막 검사는 인용이 비었거나 없는 번호를 가리키면 보류로 바꾼다. 인용한 조각이 답을 정말 뒷받침하는지는 평가에서 따로 판정한다.

## 잘 되나

평가 문항 30개(개발 20, 확인 10)로 쟀다. 문항마다 정답 근거를 원문 구절로 적어 두어, 검색이 그 구절을 가져왔는지와 답이 맞는지를 따로 본다. 판정 기준과 "어떤 결과면 무엇을 고른다"는 조건은 실행보다 먼저 커밋했고, 확인 문항은 설정을 동결한 뒤 한 번만 돌렸다. 방법과 전체 기록은 [eval/results.md](eval/results.md)에 있다.

처음에는 `text-embedding-3-small`로 시작했는데 검색이 거의 안 됐다. 한도를 물으면 벌칙 조문이 나왔고, 법령 문구를 그대로 넣어도 그 문구가 든 조각을 못 찾았다. 버그가 아닌 걸 확인한 뒤 후보 네 개를 검색만으로 비교했고, 근거를 완전히 가져온 경우가 0건에서 10건(32건 중)으로 늘어난 `text-embedding-3-large` + BM25로 바꿨다. 효과는 대부분 모델 교체에서 나왔다.

그다음 원래 궁금했던 것, 조문 단위로 자르는 게 나은지 400자씩 자르는 게 나은지를 비교했다.

| | 개발 20문항 | 확인 10문항 |
|---|---:|---:|
| 조문 단위 | 8 | 6 |
| 400자 고정 크기 | 6 | 6 |

(완전 정답 수. 답 있는 문항은 맞음, 답 없는 문항은 적절한 보류)

개발셋에서 400자 쪽만 맞힌 문항은 없었다. 400자로 자르면 한 조문의 여러 항에 흩어진 근거를 일부만 가져오는 경우가 많았다. 확인셋에서는 차이가 나지 않았다. 그래서 조문 단위를 그대로 쓴다. 대신 조각이 길어서 입력 토큰은 약 1.7배 많다.

못 맞힌 답은 대부분 검색에서 막혔다. 답 있는 문항에서 모델이 보류한 16건 중 15건이 검색이 근거를 가져오지 못한 경우였다. "법인 명의 보험", "착오송금"처럼 질문과 조문의 말이 많이 다른 문항은 어떤 설정으로도 찾지 못했다. 다음에 손볼 곳은 검색이다. 질문을 조문의 말로 바꿔 검색하거나, 긴 조문을 항 단위로 나눠 볼 생각이다.

모든 결과는 문항마다 한 번씩 돌린 것이고, 전체 실험 비용은 약 $0.27이었다.

## 실행

[uv](https://docs.astral.sh/uv/)와 Docker가 필요하다. 유료 호출을 하는 스크립트는 기본으로 비용만 추정하고, `--execute`를 붙여야 실제로 호출한다.

```bash
uv sync
uv run python scripts/fetch_laws.py    # 법령 HTML을 data/raw/로 받는다
uv run python scripts/parse_laws.py    # 조문 단위 JSONL을 data/processed/로 만든다

docker compose up -d                   # pgvector, 포트 5433
cp env.example .env                    # OPENAI_API_KEY를 채운다

uv run python scripts/index_chunks.py --model text-embedding-3-large --execute
uv run python scripts/run_eval.py --questions eval/dev_questions.jsonl --strategy article --tag test --execute
```

`select_retrieval.py`는 검색 설정 후보를 비교하고, `make_judgments.py`는 두 실행 결과로 방식 이름을 가린 판정표를 만든다. `validate_questions.py`는 문항의 근거 구절이 원문에 있는지 확인한다.

테스트는 모델 호출이나 네트워크 없이 돈다. 파싱, 조각과 지표, 그래프(가짜 모델), BM25를 대표 사례로 확인한다.

```bash
uv run pytest -v
```

## 구조

```
data/            수집할 법령 목록, 원문 HTML, 조문 단위 JSONL
src/rag_chatbot/ 파싱, 조각, 저장·검색(pgvector, BM25, RRF), LangGraph 흐름, 지표, 설정
scripts/         수집, 파싱, 색인, 검색 설정 비교, 평가 실행, 판정표, 문항 검증
eval/            평가 기준, 문항, 실행 기록, 판정표, 결과
```
